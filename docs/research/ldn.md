# LDN (Switch local communication)

Summary for our own implementation. Main source: `references/NintendoClients.wiki/LDN-Protocol.md` (kinnay). Reference implementation: `references/LDN` (kinnay, GPLv3). No key is transcribed here: cite only the name and get it from your own `prod.keys` or from the source.

## Overview

- Link layer (802.11). The host is an access point and broadcasts an advertisement action frame every 100 ms. Whoever is searching scans for these frames.
- Big-endian, unless stated otherwise.
- Versions: 2 (system 2.0 to 5.1), 3 (6.0 to 18.1, adds a challenge to authentication), 4 (19.0 onward; 20.0 adds AES-GCM and a band and channel field to the advertisement).
- Channels: 1, 6, 11 (2.4 GHz) and 36, 40, 44, 48 (5 GHz). Default: a 2.4 GHz channel. Scan with a 110 ms dwell. FRLG only scans 2.4 GHz (`references/pokeldn/docs/ldn.md`).
- SSID: 32 random hex digits, hidden in the beacon (zeroed). Discovered through the advertisement.
- IP: `169.254.X.Y`, X random per network, host always `.1`, broadcast `.255`. The host assigns Y on join.

## Authentication

1. The station associates with open authentication (standard 802.11).
2. The station sends an encrypted authentication request (data frame, EtherType `0x88B7`) within 5 s, otherwise it is disassociated.
3. The AP responds. The station resends after 700 ms without a response, up to 3 attempts.
4. A response with status 0 puts the station on the network.

Status: 0 success, 1 denied by policy, 2 malformed, 4 invalid version, 5 unexpected, 6 invalid challenge.

### Challenge (version 3+)

- Always on in games. HMAC-SHA256 with a fixed key (in the wiki and in `references/LDN/ldn/__init__.py`), over a block with the authentication token from the advertisement, a random nonce and the device id.
- According to the wiki, the goal is to detect the same purchase being used on several consoles. Our host is not a console with the game, so answering the challenge is needed to interoperate, not to share a purchase. A point to keep in mind legally (interoperability), together with the keys.

## Keys

`prod.keys` entries that the LDN library reads (`references/pokeldn/vendor/LDN/ldn/__init__.py`): `master_key_00` (protocol 1), `master_key_12` (protocol 3), `aes_kek_generation_source` and `aes_key_generation_source`. A reduced file with only these four lines is enough for the LDN path: `.secrets/ldn.keys`, generated by `swg3 keys minimize` (see [Console keys](../project/keys.md)).

Security levels: 1 (advertisement and data encrypted), 2 (advertisement only), 3 (nothing). In practice always 1.

Derivation, given a 16-byte input key and a buffer:

1. `aes_kek_generation_source` decrypted with the generation 0 master key.
2. The input key decrypted with the result of 1.
3. `aes_key_generation_source` decrypted with the result of 2.
4. The first 16 bytes of the SHA-256 of the buffer decrypted with the result of 3.

- Data: buffer = server random (16 bytes from the advertisement) + the game's passphrase (up to 64 bytes). The input key is fixed (in the wiki).
- Advertisement (AES-CTR): buffer = session info (32 bytes). Another fixed input key.
- Steps 1 to 3 do not depend on the session: the result of step 3 can be precomputed on the PC per input key. Relevant for a future standalone device (a board with no PC), which would not need to store the master key.

## Advertisement (action frame)

Header: category 127 (vendor), OUI `00:22:AA`, protocol 4, type 257. Payload:

- session info (32 bytes): local communication id (8, usually the title id), game mode (2), SSID (16 random bytes);
- LDN version, cipher type (1 plain, 2 AES-CTR, 3 AES-GCM), size, nonce;
- AES-CTR: SHA-256 hash and encrypted data. AES-GCM: 16-byte MAC and encrypted data (used more by Switch 2 games);
- data: server random, security level, accept policy, channel and band, maximum and current participants, participant list (IP, MAC, connected, platform, name, communication version), application data (up to 384 bytes, Pia format) and authentication token.

## MAC addresses

- No MAC pattern is required for the board. The Nintendo prefix that appears in the protocol is the OUI `00:22:AA` inside the advertisement action frame and the `0x88B7` data frames, not the interface address (`references/NintendoClients.wiki/LDN-Protocol.md`).
- pokeldn uses a random locally administered MAC (first byte with bit `0x02` set and `0x01` cleared) on both the AP and the station (`_random_mac` in `references/pokeldn/pokeldn/ldn/esp32_wlan.py`) and has done trades on a retail console that way. Our firmware does the same on the station when the host sends a zero MAC (`firmware/main/radio_esp32.c`); on the AP, the BSSID comes from the host.
- The MAC goes into Pia derivations (IV with `crc32(network id || source MAC)`, `ldn_constant_id`), so it must stay the same during the session, but it does not need to be Nintendo's.
- Not verified on our hardware. If the console refuses, the next test is to use a Nintendo prefix while keeping the rest random.

## Disconnection

Data frame `0x88B7`, type 259. Reasons: 3 network destroyed by the host, 4 destroyed by force, 5 station rejected.

## FRLG

- LDN identity of the GBA app, passphrase and Pia key: see `references/pokeldn/docs/ldn.md` and `references/pokeldn/pokeldn/ldn/transport.py`, `crypto.py`. Do not copy values here.
- pokeldn requires 6, 9 and 12 Mbit/s in the association response, otherwise the console drops in about 3 s (`references/pokeldn/docs/frlg_link.md`).
- The CCMP key is derived on both sides from the server random, without a 4-way handshake. The firmware installs the key directly (`references/pokeldn/docs/hardware_esp32.md`).
